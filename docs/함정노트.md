# 함정노트 — 실제로 만들면서 걸린 것들

두 편(메이클래스 "Dreamers", AIC LAB "Shine")을 만들면서 실제로 막혔던 지점들이다.
설계 당시 예상하지 못했거나 값이 달랐던 것만 적었다. **STEP을 시작하기 전에 한 번
읽어두면 대부분을 피할 수 있다.**

각 항목에 측정값을 함께 남겼다. "이렇게 하면 좋다"가 아니라 "이 값이 이랬고
이렇게 바뀌었다"로 적는 것이 이 문서의 규칙이다.

## A. Windows 인코딩 — 모든 스크립트

**증상 1 (인코딩)**: `prepare_env.py --check`조차 실행되지 않고
`UnicodeEncodeError`로 죽는다.

**원인**: 상류 도구 스크립트가 안내문을 중국어로 출력하는데 Windows 콘솔 기본
인코딩이 `cp949`다.

**증상 2 (디코딩)**: `PYTHONIOENCODING=utf-8`을 붙였는데도 가상환경 생성 중에
긴 트레이스백이 찍힌다.

```
UnicodeDecodeError: 'cp949' codec can't decode byte 0xed in position 107
```

**원인**: `PYTHONIOENCODING=utf-8`은 **자식 프로세스의 출력만** UTF-8로 만든다.
부모는 여전히 로케일(`cp949`)로 디코딩하려 한다. 경로에 한글이 들어 있으면
(`C:\project\강의_프로젝트\...`) 그 한글 바이트에서 터진다.
가상환경은 그래도 만들어지지만 실패한 것처럼 보인다.

**조치**: `PYTHONIOENCODING` 대신 `PYTHONUTF8=1`을 쓴다. 이건 **입출력과
서브프로세스 디코딩을 모두** UTF-8로 맞춘다.

```bash
PYTHONUTF8=1 python scripts/prepare_env.py
```

**측정값**: Python 3.14.4 / Windows 11 / 경로 `C:\project\강의_프로젝트\...`

| 설정 | 결과 |
| --- | --- |
| 없음 | `UnicodeEncodeError` — 실행 안 됨 |
| `PYTHONIOENCODING=utf-8` | 환경은 생성되나 `UnicodeDecodeError` 트레이스백 |
| `PYTHONUTF8=1` | 깨끗하게 완료, exit 0 |

관련 STEP: 01부터 전부.

## C. 출력이 16:9가 아니다

**증상**: `--cap-long-edge 2560`을 주면 출력이 **2560x1420**이다.
비율 1.803으로, 16:9(1.778)가 아니다.

**결과**: 그대로 1920x1080으로 내보내면 가로가 1.4% 눌린다.

**조치**: 켄번즈 전에 16:9를 먼저 확보한다.

```
crop=2524:1420:18:0
```

## F. 종이 텍스처가 마지막 프레임에서 한꺼번에 튀어나온다

가장 눈에 띄는 결함이었다.

**증상**: 그림이 다 완성되는 순간 화면 전체 색감이 확 바뀐다.

**원인**: 렌더러는 원본 모서리에서 샘플한 **단색**으로 캔버스를 칠하고 그 위로
그림을 드러낸다. 그래서 **어떤 영역에도 속하지 않은 픽셀은 전부 마지막에 갑자기
나타난다.** 생성 이미지에 얼룩·금·비네팅이 있으면 완성 순간 전체가 바뀐다.

**측정값**: 영역 검출을 돌리면 33개 덩어리 중 **28개가 얼룩**이었다.

**조치 1 (예방, 권장)**: K절 참조. 프롬프트에 명시해 애초에 막는다.

**조치 2 (사후 보정)**: 재생성하지 말고 배경을 평탄화한다. 저주파 배경장을
추정해 빼는 플랫필드 보정이라 그림 선과 강조색은 그대로 남는다.

1. 1/8로 축소 → 강한 미디언 블러 → 원래 크기로 확대 = 배경장
2. `원본 - 배경장 + 목표종이색`
3. 밝고 저채도인 픽셀만 목표색으로 스냅 (채도 높은 강조색은 보존)

**결과**: 모서리 표준편차가 4.6~5.3에서 **0.04~1.11**로 떨어졌다.

## G. `parse_srt.py`의 분경 제안은 음악을 모른다

**증상**: 도구가 제안한 막 경계가 곡의 전환점과 어긋난다.

**측정값**: Dreamers에서 도구 제안은 1막을 6초부터 시작해 **인트로 6초를 누락**시키고,
3막을 16.76초로 잘라 **자기 최소 기준(25초)마저 어겼다.**

**원인**: 알고리즘이 자막 길이만 보고 30초에 맞춘다.

**조치**: 막 경계는 오디오 RMS 에너지의 전이점에서 잡는다.
Dreamers 실측: 33초 `0.131` → 34초 `0.194` 급상승, 63~65초 골짜기 후
66초 `0.240` 반등. 이 지점들이 곡이 실제로 꺾이는 곳이다.

## I. 실측값 — 시간과 크기

Dreamers 기준.

| 항목 | 값 |
| --- | --- |
| 렌더 시간 (2560px, 30fps) | 1막 3분33초 / 2막 2분45초 / 3막 2분33초 = 약 9분 |

```bash
ffprobe -v error -count_frames -select_streams v:0 \
        -show_entries stream=nb_read_frames -of csv=p=0 <막.mp4>
```

## J. 켄번즈 팬은 이동 최대치까지 가면 안 된다

두 번째 작업(Shine)에서 나왔다.

**증상**: 마지막 프레임에서 인물의 왼쪽이 66px 잘렸다.

**원인**: 팬을 이렇게 짰다.

```
x='(iw-iw/zoom)*(on/(N-1))'
```

이러면 마지막 프레임에서 **이동 가능한 최대치**까지 밀린다. 줌 1.13에서 가능한
오프셋이 290px인데 가장 왼쪽 요소가 225px 지점에 있었다.

켄번즈에서 무언가 화면 밖으로 나가는 건 정상이지만 **인물이 반쯤 잘리면 의도가
아니라 실수로 보인다.**

**조치**: 팬 폭에 계수를 곱해 양쪽 여유를 남긴다. 계수는 눈대중하지 말고 계산한다.

```
끝 오프셋 = (크롭폭 - 크롭폭/최대줌) × 계수
조건: 끝 오프셋 <= 가장 왼쪽 요소의 x
      끝 오프셋 + 크롭폭/최대줌 >= 가장 오른쪽 요소의 x + 폭
```

**측정값**: 이 장면에서 계수 100%는 잘렸고, 75%는 여유 7px로 아슬아슬했고,
**50%가 80px 여유로 안전**했다.

원본 좌표를 렌더 좌표로 옮길 때 **해상도 스케일과 16:9 크롭 오프셋을 함께
적용**해야 값이 맞는다.

## L. 렌더러 기본 fps가 60이다 — 켄번즈가 절반에서 끝난다

**증상**: 렌더는 잘 됐고 길이도 맞는데, 켄번즈를 얹으면 카메라 무빙이 영상
중간에서 멈춰 있고 뒤 절반은 정지 화면처럼 보인다.

**원인**: `scripts/stream_render.py`의 `fps` 기본값이 **60**이다
(주석: "고주파 출력으로 펜 끝 움직임을 연속에 가깝게").
그런데 `kenburns_and_mux.sh`의 `N1 N2 N3`은 **30fps 기준 프레임 수**다.

```
N1=1020; N2=930; N3=683      # 34.0 / 31.0 / 22.76초 × 30fps
```

`zoompan`의 `on/(N-1)` 식이 실제 프레임 수의 절반을 전체로 착각하므로,
무빙이 절반 지점에서 끝난다.

**측정값**: 같은 선화·같은 annotation·같은 `--total-ms 34000`으로 렌더한 결과.

| 명령 | 출력 | fps | 프레임 수 |
| --- | --- | --- | --- |
| `--cap-long-edge 2560` | 2560x1420 | 60 | 2040 |
| `--cap-long-edge 2560 --fps 30` | 2560x1420 | 30 | **1020** ← 기준본과 일치 |

**조치**: `--fps 30`을 붙인다. 최종 출력이 30fps이므로 여기서 맞춰두는 게
파일도 작고 켄번즈 계산도 맞는다.

굳이 60fps로 렌더하고 싶으면 켄번즈 스크립트의 `N` 값을 두 배로 바꾼다.
어느 쪽이든 **렌더 결과의 실제 프레임 수를 읽어서 넣는 것**이 안전하다
(I절 하단의 `ffprobe` 명령).

## M. 영역 검사도의 한글 라벨이 □□□로 나온다

**증상**: `render_annotation_preview.py`로 만든 영역 검사도의 라벨이
`3. □□□ □ top_to_bottom` 처럼 네모로 나온다. 확인 관문에 쓰는 그림인데
정작 뭐가 뭔지 읽을 수 없다.

macOS·Linux에서는 아예 이렇게 죽는다.

```
FileNotFoundError: cannot open resource: 'C:/Windows/Fonts/msyh.ttc'
```

**원인**: 원본 스크립트가 폰트를 한 줄로 고정해 뒀다.

```python
font_file = "C:/Windows/Fonts/msyh.ttc"     # Microsoft YaHei
```

Microsoft YaHei는 중국어 폰트라 **한글 글리프가 없다.** 그리고 이 경로는
Windows에만 있다.

**조치**: **이 레포에서는 이미 고쳐 뒀다.** `FONT_CANDIDATES` 목록을 순서대로
탐색해 한글이 있는 폰트를 먼저 쓴다.

| 우선순위 | 폰트 | OS |
| --- | --- | --- |
| 1 | `C:/Windows/Fonts/malgun.ttf` (맑은 고딕) | Windows |
| 2 | `C:/Windows/Fonts/NanumGothic.ttf` | Windows |
| 3 | `AppleSDGothicNeo.ttc` | macOS |
| 4 | `NanumGothic.ttf` · `NotoSansCJK-Regular.ttc` | Linux |
| 5 | `msyh.ttc` (원본 기본값) | 최후 |

전부 없으면 PIL 기본 폰트로 떨어지고 경고를 출력한다. 죽지는 않는다.

이건 상류 코드에 손을 댄 유일한 곳이다. `NOTICE.md`에 표기해 뒀다.

관련 STEP: 06.
